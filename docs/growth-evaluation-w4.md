# Marketing control-plane W4 contract: outcome evaluation

W4 answers one question for an approved initiative: what did the goal's metric
record before and after the initiative's actions, and can those two windows
be compared? It is a descriptive reading, not causal attribution.

It never claims incremental growth, causal lift, revenue generated by an
action, marketing-attributed conversions or return on marketing investment.
`COMPARABLE` describes measurement quality only. It is not a success label.

## What it reuses

W4 adds no migration, no table and no stored outcome. Each request reads:

| Input | Source |
| --- | --- |
| Initiative, status and human decision history | W0 `GrowthRepository.get` (`growth_opportunity_documents`) |
| Goal and its immutable metric definition | W0 `growth_goal_documents`, bound by the initiative's `goalId` |
| Latest measurement plan, plan timing and declaration count | W3 `GrowthMeasurementRepository.plan` and `growth_measurement_plans` |
| Per-day values for each window | W3 `GrowthMeasurementRepository.series`, called once per window for the goal's definition |
| Recorded actions | W1 ledger: `interventions`, joined to `growth_initiative_actions` |

`GrowthEvaluationRepositoryLive` is part of the W0 extension point,
`GrowthRepositoriesLive`, so existing server and test layers pick it up
without being rewired. The repository gathers the inputs, then calls the pure
function `evaluateGrowthOutcome` (`packages/db/src/growth-evaluation-rules.ts`).
That function has no I/O and no clock: identical input gives an identical
evaluation. The database time arrives as `asOf`.

## Endpoint

`GET /api/growth/clients/:id/opportunities/:opportunityId/evaluation` returns
`{ evaluation: GrowthOutcomeEvaluation }`.

The endpoint requires an operator session from the same origin, like the other
growth routes. It returns:

- `401` without a session.
- `404` (`GrowthNotFound` / `OpportunityNotFound`) for a foreign business or
  initiative. Nothing from the other account is echoed.
- `422` for malformed ids.

It is read-only. The integration suite checks that the growth, measurement and
ledger row counts are unchanged after two evaluations. The Operator Agent gets
no new tool.

## Measurement semantics

- **Exact definition.** Both windows are read only for the goal's own metric
  definition id and version.
  - A plan or series bound to another definition is reported as
    `METRIC_DEFINITION_MISMATCH`. It is never read across or merged.
  - Imports for other definitions that overlap the period are listed as the
    caveat `OTHER_METRIC_VERSIONS_EXCLUDED`.
- **Exposed metadata.** The response carries the label, source kind, source
  identity, GA4 event, property, counting semantics, unit, currency and
  reporting time zone.
- **Calendar days.** Days are calendar days in the definition's reporting time
  zone. Action timing uses `performedAt` (operator-asserted) converted to that
  zone, shown as `performedDay`. `recordedAt` is shown alongside it and never
  used for windowing.
- **Per-window fields.** Each window reports:
  - `days`, `validDays`, `coverage`.
  - The exact `missingDays`, `unavailableDays`, `conflictingDays` and
    `syntheticDays`.
  - `validTotal`.
  - `dailyMean = { total, days, value }`.
  - The raw W3 `series` and `conflicts`.
- **Valid days.** A valid day is `OK` with `REAL` origin. Missing and
  unavailable days are never zero. Synthetic and conflicting values never
  enter totals.
- **`comparison`.** It exists only when the status is `COMPARABLE`.
  - `totalDifference` is given only when both windows have the same length.
    Otherwise `basis` is `DAILY_MEAN_ONLY` and the caveat
    `UNEQUAL_WINDOW_LENGTHS` is added.
  - `dailyMeanPercentChange` is `null` when the baseline mean is zero
    (`ZERO_BASELINE`).
  - Rounding: means and differences to 2 decimals, percentages to 1 decimal,
    coverage to 4 decimals.
- **Currency metrics.** `SUM`/`CURRENCY_MINOR` metrics are rejected with
  `CURRENCY_AGGREGATION_UNSUPPORTED`. No series is read for them.

## Status and reasons

`status` is `INDETERMINATE` whenever at least one blocking reason exists.
Otherwise it is `COMPARABLE`. Reasons and caveats come back in the canonical
order below. Each one carries `{ code, detail, refs }`, where `refs` holds the
affected days or action ids.

| Blocking reason | When |
| --- | --- |
| `INITIATIVE_NOT_APPROVED` | No `APPROVED` event exists in the decision history |
| `CURRENCY_AGGREGATION_UNSUPPORTED` | The goal metric is not `EVENT_COUNT`/`COUNT` |
| `NO_MEASUREMENT_PLAN` | No plan has been declared |
| `METRIC_DEFINITION_MISMATCH` | The plan or a series does not match the goal's definition id, version, time zone or window |
| `INVALID_WINDOWS` | The windows are not ordered real days with the baseline ending before the observation starts |
| `PLAN_DECLARED_AFTER_EXECUTION` | W3 timing is `DECLARED_AFTER_EXECUTION` |
| `NO_RECORDED_EXECUTION` | The initiative has no current linked action |
| `EXECUTION_TIMING_INCOMPATIBLE` | One of the initiative's actions falls outside `baselineEnd < performedDay ≤ observationStart` |
| `OBSERVATION_INCOMPLETE` | `observationEnd` is today or later in the metric time zone |
| `MISSING_DAYS` / `UNAVAILABLE_DAYS` / `CONFLICTING_DAYS` / `SYNTHETIC_DAYS` | Any such day falls in either window. Coverage must be complete; there is no tolerance threshold |

| Caveat (non-blocking) | Meaning |
| --- | --- |
| `OPERATOR_ATTESTED_ONLY` | The initiative's actions are attested, not independently verified |
| `UNSPECIFIED_ASSURANCE` | Legacy ledger entries without channel or assurance (`UNSPECIFIED`) |
| `MULTIPLE_INITIATIVE_ACTIONS` | The windows describe several actions together |
| `OTHER_ACTIONS_IN_PERIOD` | Other initiatives' or unlinked actions fall in the period. Any difference cannot be associated with this initiative alone |
| `ACTIONS_TRUNCATED` | More than 200 actions; the list is incomplete |
| `EXECUTION_ON_OBSERVATION_START` | Part of the first observed day precedes the action |
| `UNEQUAL_WINDOW_LENGTHS` / `ZERO_BASELINE` | See comparison rules |
| `PLAN_REDECLARED` | More than one plan exists; the latest is read |
| `OTHER_METRIC_VERSIONS_EXCLUDED` | See measurement semantics |
| `INITIATIVE_CANCELLED` | The initiative was approved, then cancelled |

## Execution context

`actions` lists every current (non-superseded) ledger entry for the business
whose `performedAt` falls in the planned period (`baselineStart` to
`observationEnd`, in the metric time zone). It also lists every action linked
to this initiative, wherever it falls. Up to 200 entries are returned, oldest
first. Each entry carries:

- `type` and `channel` (null for legacy entries).
- `performedAt`, `recordedAt` and `performedDay`.
- `phase`, relative to the windows.
- `assurance` (`OPERATOR_ATTESTED`, `SYSTEM_VERIFIED` or `UNSPECIFIED`).
- `actor`, `reference` and `description`.
- `verification`.
- `association` (`THIS_INITIATIVE`, `OTHER_INITIATIVE` or `UNLINKED`) and the
  linked initiative's id and title.

Association follows the correction chain: an initiative owns every row its linked
execution's chain reaches (0030 `growth_intervention_chain_root`), so a later
correction is listed as this initiative's action with its own (possibly
`UNSPECIFIED`) assurance, never as an unrelated entry. W3 plan timing counts every
chain member, so a correction cannot hide an earlier action from the plan check.

## Workspace

Each card in the growth workspace whose decision history contains a human
approval gets a collapsed **Outcome evaluation** section. It loads on demand
and shows:

- The goal, metric and plan timing.
- The blocking reasons.
- Both windows with their gaps.
- The descriptive per-day comparison. It is labelled as "not growth caused by
  this initiative", and totals appear only for equal windows.
- Every recorded action with both times, assurance and association.
- The caveats, assumptions and limitations.

## W5 integration contract

W5 consumes W4 strictly as a read model:

1. **Entry point.** Call `GrowthEvaluationRepository.evaluate(accountId,
   businessId, opportunityId)` or the GET route. Do not reimplement the rules.
   For offline or test use, call `evaluateGrowthOutcome(input)` with a
   `GrowthEvaluationInput`.
2. **Stable codes.** Branch only on `status`, `reasons[].code` and
   `caveats[].code`. These follow `GROWTH_EVALUATION_REASONS` and
   `GROWTH_EVALUATION_CAVEATS` from `@openrecord/contracts`. Adding a code is
   additive; removing or renaming one is a breaking change. `detail` is
   operator-facing prose and is not parsed.
3. **No stored copies.** Do not persist `GrowthOutcomeEvaluation`, any window
   value or a derived score as a mutable outcome record. If W5 needs a durable
   reference, store the inputs' identities and recompute:
   - `opportunityId`
   - `plan.id`
   - `metric.id` and `metric.version`
   - `evaluatedAt`
4. **Gated numbers.** Treat `comparison` as present only when `status ===
   "COMPARABLE"`. Never surface `baseline`/`observation` means as a comparison
   when the status is `INDETERMINATE`.
5. **No causal language.** Any summary, review prefill or agent text built on
   W4 must keep `interpretation: "DESCRIPTIVE_ONLY"` and the `limitations`.
   It must not describe the difference as lift, attribution, ROI or success.
   A human review conclusion (`KEEP`/`REVERT`/`EXTEND`/`INCONCLUSIVE`) stays a
   human decision; W4 never pre-selects it.
6. **Assurance stays separate.** An `OPERATOR_ATTESTED` action is never
   upgraded or shown as verified. Only a future adapter-written
   `SYSTEM_VERIFIED` ledger entry changes `assurance`.
7. **Currency.** `CURRENCY_AGGREGATION_UNSUPPORTED` stays until a tested
   SUM/CURRENCY_MINOR aggregation lands in both W3 (imports and guards) and the
   W4 rules.

## Non-goals

No causal model, control group, seasonality adjustment, significance test,
forecast, threshold-based success label, scheduled evaluation, alert, stored
outcome, agent tool or migration.
